## ١) النتيجة باختصار

- **225 و226 مطبّقتان كاملتين ومطابقتان للملفات حرفياً.** غيابهما عن السجلّ لأنهما لُصقتا في SQL Editor، لا لأن شيئاً ناقص.
- **المشكلة أوسع من 225 و226:** جدول `supabase_migrations.schema_migrations` ليس سجلّ هجرات المشروع أصلاً. هو أثر استدعاءات `apply_migration` من الأداة فقط. كل ما لصقه المالك في SQL Editor (أكثر من نصف الملفات) غير مسجَّل فيه.
- **لا شيء في المشروع يقرأ هذا الجدول:** لا مجلد `supabase/migrations`، ولا `supabase db push`، ولا فروع Supabase. غيابُ صفّ فيه لا يغيّر سلوك أي شيء.
- **لذلك «تصحيحه» لا يجعله مصدر حقيقة.** المقترح: مصدر الحقيقة = ملفات `sql/` + فاحص يقارنها بالقاعدة الحيّة، وتسجيل ذاتي في السجلّ من 227 فصاعداً.

```sql
insert into supabase_migrations.schema_migrations (version, name, created_by, idempotency_key)
select to_char(clock_timestamp() at time zone 'utc', 'YYYYMMDDHH24MISS'),
       '227_ops_foundation', 'sql-editor', 'tilal:file:227_ops_foundation'
 where not exists (select 1 from supabase_migrations.schema_migrations where name = '227_ops_foundation')
```

## ٦) آلية التسجيل المعتمدة (Q14)

### ٦-١) بنية السجلّ الفعلية (فُحصت 2026-11-26)

| العمود | النوع | ما تكتبه أداة Supabase اليوم | ما يكتبه إطار Tilal |
|---|---|---|---|
| `version` | text **PK** | طابع UTC بـ14 رقماً | نفس الصيغة، وأكبر من كل نسخة سابقة بثانية على الأقل |
| `name` | text | اسم الهجرة | اسم الملف بلا `.sql` (`227_ops_foundation`) |
| `statements` | text[] | نصّ الهجرة كاملاً | سطر مرجعي إلى الملف في git (الملف لا يستطيع تضمين نصّه) |
| `created_by` | text | بريد المستخدم | `sql-file:<current_user>` (لا بريد شخصي في ملفات المشروع) |
| `idempotency_key` | text **UNIQUE** | فارغ في كل الصفوف الـ176 | `tilal:<name>` — القيد الفريد للجدول نفسه يمنع التسجيل مرتين |
| `rollback` | text[] | فارغ | فارغ (الرجوع في ملف `rollback_*` بلا رقم، كالعادة) |

لا جدول موازٍ، ولا قيد أو فهرس جديد على مخطط Supabase المُدار.

### ٦-٢) الإطار

`sql/templates/migration_frame.sql` يولّده `node staging/tools/new-migration.mjs <name> "<title>" <body.sql>`:

```
begin;                                   ← الملف كله معاملة واحدة صريحة
  رأس: إن وُجد الاسم أو المفتاح في السجلّ ⇒ MIGRATION_ALREADY_APPLIED (لا شيء يُنفَّذ)
       وإلا: إدراج صفّ التسجيل
  … محتوى الهجرة …
  ذيل: التأكد من صفّ التسجيل
commit;
```

| المتطلب (Q14) | كيف يتحقق |
|---|---|
| التنفيذ والتسجيل في معاملة واحدة | `begin`/`commit` صريحان في الملف؛ الصفّ يُدرج داخلها؛ المولّد يرفض محتوى فيه `begin`/`commit` خاص به؛ `run-sql.ps1` لا يغلّفه بـ`-1` |
| لا تسجيل مرتين | فحص الاسم والمفتاح في الرأس + القيد الفريد `schema_migrations_idempotency_key_key` |
| لا تطبيق مرتين | الرأس يرفض قبل أي تغيير |
| لا تسجيل إن فشل أي جزء | أي خطأ ⇒ المعاملة تُلغى ⇒ الصفّ يختفي معها؛ وpsql/SQL Editor يتوقفان عند أول خطأ |
| متوافق مع سجلّ Supabase | الجدول نفسه، والأعمدة نفسها، وصيغة النسخة نفسها؛ يظهر في لوحة Supabase كبقية الصفوف |

**حدّ معروف:** لا تُرسل هذه الملفات عبر `apply_migration` (الأداة تسجّل صفّها بعد التنفيذ ⇒ اسم مكرّر). طريق التطبيق: اللصق في SQL Editor (الإنتاج، بعد الموافقة) أو `staging/run-sql.ps1` (staging).
